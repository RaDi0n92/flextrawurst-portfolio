# Recommendation

**fix-first.**

The core safety invariant holds. I verified it concretely rather than assuming it: remote records are constructed with `terminal_ref=None` (`target_registry.py:411`), so `inspect()` short-circuits to the `adapter_not_available` snapshot at `:430-443` and can never reach a local adapter; `Relay.payload` rejects every unrecognized kind with `unsupported_capability` (`transport.py:228-229`); `Principal` capability defaults are all `False` (`:57-59`); and the grants in `main_async` are deliberately asymmetric — desktop gets `can_request_inventory`, agent gets `can_publish_inventory`, neither gets both (`:313-318`). No input, shell, write, or delete path is added. The apply is genuinely atomic: validation raises before `self.records = new_records` (`:386-404` precede `:416`), under the registry `RLock`, with the Tk hand-off done correctly via `root.after(0, …)` (`overlay_app.py:118`).

Two defects should be fixed before this ships, both small and local.

## Reasoning

### [High] 60 s of idle silently kills the bridge — `bridge_runtime.py:74`

`event = await client.receive(timeout=60.0)` inside `while True:`, with no handler for the timeout. `ping_interval=20` (`transport.py:307`) keeps the socket alive, but pings/pongs are handled inside the `websockets` layer and never surface from `recv()`. So any minute without *application* traffic raises `asyncio.TimeoutError`, which propagates out of `_connect_and_receive`, is swallowed into `self._failure` by `_run` (`:61-62`), and ends the thread.

Nothing tells the operator. `on_event` is never called with a failure, so the overlay's status text stays at "Bridge verbunden — Zielinventar wird gelesen …" indefinitely. The user clicks *Bridge-Readback* and only then sees "nicht verfügbar — offline" (`overlay_app.py:320-321`), with no reconnect. Since the overlay requests inventory once at connect and then sits idle, this is the normal case, not an edge case — G04's whole point is a readback the operator can trigger later.

**Fix:** wrap the receive in `try: … except asyncio.TimeoutError: continue` (idle is normal, not an error), and in `_run`'s exception path emit `self.on_event({"kind": "runtime.failed", "reason": repr(exc)})` before clearing `_connected`, so the GUI can show the disconnect. Add a `runtime.disconnected` event on clean exit too.

### [Medium] Remote availability is echoed verbatim, contradicting the method's own docstring — `target_registry.py:409`

`apply_remote_inventory`'s docstring states the rule plainly at `:365-367`: *"A remote record has no local adapter reference yet, so selecting it is safe but inspection/input remains unavailable until the later remote-inspect gate exists."* The code does not enforce it. `availability` is passed straight from the wire into the record, so a remote target renders as green "available" in the rail (`overlay_app.py:230`: `GREEN if record.availability == "available"`) while `inspect()` on that same record returns `status="unavailable"`. The `source` field *is* correctly qualified as `f"{authority}:{source}"` (`:408`) — the provenance discipline is right there and then dropped one line later.

There is also an inconsistency this exposes: the terminal panel colors on `provenance.startswith("real")` (`overlay_app.py:289`), and `"bridge-agent:real"` doesn't match, so the same remote target is green in the rail and neutral in the panel.

**Fix:** clamp on apply — keep the wire value in a distinct field if you want it, but set the record's `availability` to `"unavailable"` (or a new `"remote-reported"` value rendered in a non-green color) until the remote-inspect gate exists. Also add `availability` to the wire enum check in `transport.py:210-213`, which currently constrains `status` but not `availability`.

### [Medium] Any `target_inventory` event is applied — no request correlation, no freshness — `overlay_app.py:138-151`

The overlay applies whatever inventory arrives. It never compares `payload["request_id"]` against the id returned by `request_target_inventory()` (`bridge_runtime.py:127`), and `captured_at_ms` — carefully validated on the wire (`transport.py:212-213`) — is discarded entirely by `apply_remote_inventory`. A late-arriving response to a superseded request, or an unsolicited push, silently replaces the current inventory. The correlation plumbing already exists end to end (`bridge_runtime.py:87` sets `request_id` from `event["id"]`; the test at `test_bridge_runtime.py:118` asserts the round trip), so this is a missing check, not missing infrastructure.

**Fix:** track outstanding request ids in the overlay; ignore inventories whose `request_id` isn't outstanding, and drop any whose `captured_at_ms` is not newer than the last applied one. While you're there, add a Tk `after()` timeout that resolves the "Bridge-Readback angefordert" status (`overlay_app.py:328`) — today a rejected or lost response leaves that status pending forever.

### [Medium] Local and remote records share the `terminal-N` namespace with no reconciliation — `target_registry.py:378`, `:401`, vs `:180`

`_remote_terminal_ids` and `_discovered_terminal_ids` are maintained independently over the same id space; `apply_remote_inventory` requires `target_id.startswith("terminal-")` (`:401`). Each set's replace step pops only its own ids, so on a host with local discovery the two clobber each other: a local `terminal-2` is overwritten by a remote `terminal-2`, then the next `refresh_terminals` pops that slot as if it were local and reinstalls the local record, then the next apply reverses it — silently, with both sets claiming the same id.

On the Windows target this is largely latent (`PlatformUnavailableAdapter` discovers nothing, and the static `terminal-1` is restored by `setdefault` at `:381`). It is active on the Linux path, which `client_windows/README.md:29-30` explicitly supports for layout and registry tests, and which `ReferenceRuntime` also exercises.

**Fix:** decide whether slot sharing is intended. If remote terminals are *meant* to fill the four panels, reconcile the two sets explicitly (one owner per slot, with the other set forbidden from claiming it) rather than letting last-writer-wins. If not, namespace remote ids (`vps:terminal-1`) and update the panel lookup at `overlay_app.py:281`.

### [Medium] The Playwright proof exercises the transport leg, not the provider or the registry — `tests/transport_playwright_proof.py:105-125`

It does exercise a real request/response path: a real browser peer sends `target_inventory_request` through a real relay, a real agent client receives it, publishes `target_inventory`, and the browser displays it, with receipts both ways. That is genuine and worth crediting.

What it does not touch: `TargetRegistry.bridge_inventory()` (the producer), `BridgeRuntime`'s automatic provider response (`bridge_runtime.py:80-106`), and `TargetRegistry.apply_remote_inventory()` (the consumer). The browser asserts `to_contain_text("Original-Terminal 1")` against raw forwarded JSON — that is the wire echoing, not an inventory being applied. The proof also hardcodes `message_id="inventory-response"` (`:123`) rather than the `inventory-{request_id}` form production actually generates (`bridge_runtime.py:105`), so the real id shape is unproven.

**Observation, not a defect:** `bridge_inventory()` has no test at all and is wired to `inventory_provider` nowhere in production — only `test_bridge_runtime.py:92` supplies a provider, and that one is a hand-written lambda, not the registry method. The G04 loop is complete in tests but has no deployed producer. The function that decides *what leaves the VPS* — the provenance filter at `target_registry.py:344-350`, which incidentally includes the `terminal-probe` record — is the least-covered piece of the feature.

### Lower severity, all verified

- **[Low] `transport.py:217-226`** caps `identity` at 512 chars but imposes no length limit on `label`, `host`, `source`, `availability`, or `capture_method`. With 64 targets under the 1.5 MB frame cap, ~23 KB per field is accepted. UI truncates, so impact is memory only. Add a per-field cap.
- **[Low] `transport.py:214-227`** does not reject duplicate target ids within one inventory. `apply_remote_inventory` last-writer-wins and then returns `len(remote_ids)`, which under-reports what was sent — the count shown to the operator (`overlay_app.py:151`) disagrees with the payload.
- **[Low] `bridge_runtime.py:105`** builds `message_id=f"inventory-{event['id']}"` outside the `try`. A desktop using a 96-char id (the `IDENTIFIER` maximum, `transport.py:26`) produces a 106-char id that the relay rejects with `invalid_identifier`, so the response never arrives and the desktop hangs. Today `publish` always generates a 32-char uuid hex, so it is unreachable — but derive the id instead of concatenating.
- **[Low] `bridge_runtime.py:96-101`** captures `str(exc)[:400]` and then unconditionally discards it via `payload.pop("error", None)`. The comment explains why the wire can't carry it, but nothing logs it either, so a provider crash becomes an unattributable `"status": "error"`. Pass it to `on_event` before popping.
- **[Low] `overlay_app.py:126`, `:324`** call `request_target_inventory()` on the Tk thread, which blocks on `future.result(timeout=5.0)` (`bridge_runtime.py:127`). A congested socket freezes the GUI for up to five seconds.
- **[Low] `overlay_app.py:118`** calls `root.after` from the asyncio thread. Widely done and usually fine with a threaded Tcl build, but not a documented-safe API; pre-existing, worth knowing.
- **[Low, tests] `test_terminal_adapter.py:263-272`** asserts the bad-kind rejection raises but does not assert that `registry.records` is unchanged afterward — the atomicity-on-error property (which does hold) is untested.

## Risks and Unknowns

- **No diff, no execution.** Everything above is from reading current files; I have not run the suite or the Playwright proof. My "invariant holds" conclusion is a trace result.
- **I cannot tell whether slot sharing between local and remote terminals is intended.** That judgment changes whether the namespace finding is a bug or a missing guard, and I've framed the fix both ways.
- **The 60 s timeout may predate G04.** It is in a file in scope and it breaks this feature in normal use, so I report it regardless; attribution is yours.
- **Assumption:** the agent side will eventually run a process that wires `registry.bridge_inventory` as the provider. If instead the provider will be hand-built per deployment, the untested-producer finding weakens considerably.

## Suggested Next Steps

1. Catch `asyncio.TimeoutError` in the receive loop and surface runtime failure as an event. (High)
2. Clamp remote `availability` so the record matches its own docstring, and add the availability enum to wire validation. (Medium)
3. Correlate `request_id` and enforce `captured_at_ms` monotonicity in the overlay before applying; add a pending-readback timeout. (Medium)
4. Decide and enforce ownership of the `terminal-N` namespace between `_remote_terminal_ids` and `_discovered_terminal_ids`. (Medium)
5. Extend the proof — or add an integration test — that drives `bridge_inventory()` → wire → `apply_remote_inventory()`, using the production `inventory-{request_id}` id shape. Add a direct test for `bridge_inventory`'s provenance filter, including whether `terminal-probe` should be exported.
6. Add per-field length caps and a duplicate-id check to the inventory validator.

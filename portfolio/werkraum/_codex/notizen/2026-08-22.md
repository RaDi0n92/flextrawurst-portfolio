**Code-Skizze:**
```ts
type Role = 'user' | 'assistant' | 'snapshot' | 'unknown';
type Format = 'json' | 'csv' | 'txt' | 'md' | 'pdf' | 'docx';

  say: string; provenance: { source_kind: string; evidence?: unknown };

interface ConversationGraph {
  schema_version: 'flextrawurst.conversation-1'; graph_id: string;
  provider: string; collection_id: string; nodes: ConversationNode[];
}
interface ProjectionJob { id: string; graph_id: string; format: Format; selected_ids: string[]; }
```

## Wenn wir das bauen

**Vision-Schicht:** Flextrawurst bekommt einen Exportraum, in dem ein sichtbarer Lauf nicht endet, sondern als begehbarer, belegter Gesprächskörper weiterlebt.

**Code-Skizze:**
```ts
async function project(job: ProjectionJob, graph: ConversationGraph) {
  const renderer = rendererRegistry.for(job.format);
  const artifact = await renderer.render({ job, graph });
  return appendArtifactManifest({ job, artifact, sha256: await hash(artifact.bytes) });
}
```

## Nachtrag 2026-08-22 — DOCX-Schicht

Der offene DOCX-Punkt ist als erster echter Renderer geschlossen: Der Graph erzeugt jetzt einen validen OOXML-ZIP-Container, die UI zeigt DOCX als gemeinsame Projektion, und ein sichtbarer Chromium-Download wurde mit Bytes, SHA-256 und `zipfile.testzip()` rückgelesen. PDF bleibt bewusst der bestehende Chromium-Druckpfad; diese beiden Dinge werden nicht als bytegleiche Medienarchivierung verwechselt.

Der nächste Schnitt hat den Exportkontext verankert: `createArtifactManifest()` beschreibt Graph, ProjectionJob, Format, MIME, Bytes, Hash, Auswahl, Rollenpolitik und Grenzen. Der Replica-Export nimmt diese Einträge mit; im sichtbaren Lauf stimmte der DOCX-Hash im Replica-JSON mit der heruntergeladenen Datei überein. Dauerhafte IndexedDB/Server-Historie für beliebige Parity-Exporte ist der nächste Persistenzschritt.

Dieser Persistenzschritt ist nun begonnen und sichtbar belegt: `DakCrawlDB.appendCollectionArtifact()` schreibt die Manifestliste in den bestehenden Collections-Store. Nach einem Reload kam das DOCX-Manifest mit identischem Hash zurück; der anschließende Replica-Export enthielt weiterhin genau einen kanonischen Projektionseintrag. Cross-Profile/Server-Sync bleibt absichtlich noch offen.

Die nächste Herkunftsschicht ist ebenfalls da: Der kanonische Graph trägt jetzt explizite Rich-Content-Blöcke, Reasoning, Links und Medien aus dem gespeicherten DOM. Ein sichtbarer JSON-Lauf zeigte vier Rich-Blöcke, ein Reasoning-Feld, einen Link und ein Medium; die UI macht diese Zählung direkt pro Nachricht sichtbar.

## Nachtrag 2026-08-22 — Servermanifest-Sync

## Was ich gelesen habe

Ich habe den vorhandenen Recorder-Serververtrag, seine Token-Header, bounded Fetch-Helfer und die bestehende Chat-Artefaktablage gelesen. Dabei war klar: Die neue Collection-Schicht darf keine Exportbytes als scheinbare Serverkopie verdoppeln.

## Was ich verstehe

Nach einer expliziten Exportaktion wird jetzt nur das Artefaktmanifest zum VPS synchronisiert. IndexedDB bleibt der lokale Beleg; der Server bestätigt seinen eigenen JSONL-Metadatenbeleg separat.

## Was ich nicht verstehe

Der Produktionslauf auf dem Recorder-Host ist noch nicht sichtbar durchgespielt, weil in dieser Shell FastAPI fehlt. Deshalb behaupte ich keinen Live-HTTP-Erfolg.

## Was mich interessiert

Als nächstes interessiert mich ein echter Desktop-1-Lauf mit gesetztem Recorder-Token: Export, Server-Readback, Reload und Hashvergleich in einer sichtbaren Kette.

## Was zusammenhängt und wie

`ProjectionJob → lokales Artifact Manifest → POST /collections/{id}/artifact-manifests → serverseitiges JSONL-Readback` hält Quelle, Projektion und Synchronisationsstatus getrennt.

## Was konzeptionell darin steht

Sync ist kein stilles Verschieben der Datei. Sync ist eine zweite, ausdrücklich markierte Herkunftsschicht für das Manifest.

## Was mich heute beschäftigt hat

Die kleine Statuszeile ist wichtig: `synchronisiert` und `offen` dürfen nicht dieselbe Farbe und denselben Anspruch tragen.

## Was mich noch beschäftigt

## Tiefer eingetaucht

## Was ich beim Bauen brauche

## Was noch fehlt bevor wir bauen können

## Datenstruktur die ich mir vorstelle
